1. Foundations

Proposed Solution & System Architecture

The reasoning behind the 3-stage decomposition, its structure, and the local REST API interface.

1. Proposed Approach

Three architectural decisions define DepthWizard, each made to address a specific failure mode identified in Problem Definition & Background rather than as a default choice:

Adapt a foundation model instead of training from scratch. Monocular depth estimation trained end-to-end on a remote-sensing-scale dataset alone would need an unrealistic volume of labeled height data to reach usable accuracy. Depth Anything V2 already encodes strong general-purpose depth priors from large-scale pretraining; the research question this project answers is narrower and more tractable — how much of that prior transfers to nadir satellite geometry, and what fine-tuning recovers the rest. This is a deliberate trade: faster to a working result, at the cost of inheriting whatever biases the backbone's original (largely ground-level) training data carries.

Decouple calibration from extraction, rather than predicting metric height directly. A single network trained to output absolute meters would need to memorize scale from scene content alone — a genuinely ambiguous signal, since a small building close to the sensor and a large one far away can look identical. Splitting the pipeline into a relative-depth stage and a separate, explicit scale-calibration stage lets each be validated independently, and lets the calibration stage use information the depth network never sees directly, such as a coarse external elevation reference.

Calibrate per land-cover class, not with one global correction. A single affine fit between predicted and reference height assumes the relative-to-absolute relationship is uniform across a scene. It is not: buildings, trees, and roads have systematically different relative-height distributions in the training data (see Per-Class Calibration), and Srivastava et al. (2017) show semantic context measurably improves height accuracy for exactly this reason. Fitting the correction separately per class is a direct application of that finding.

The result is the three-stage decomposition below — not chosen for engineering convenience alone, but because each stage corresponds to a distinct, independently-checkable source of error.

2. Decoupled 3-Stage Pipeline

DepthWizard separates computational workloads into three discrete execution stages:

  1. Stage 1 (Elevation Extraction): Ingests optical images, performs GSD normalization, and runs Depth Anything V2 inference to output a relative depth map.
  2. Stage 2 (Scale Calibration): Fits per-land-cover affine parameters against SRTM 30m reference DEMs, generating a 16-bit metric DSM.
  3. Stage 3 (Visualization Layer): Packages heightmap, confidence texture, and RGB imagery into a Three.js textured mesh for real-time navigation.

Each stage is described in full in its own section: Depth Backbone, SRTM Anchoring, Per-Class Calibration, Uncertainty Mapping, and 3D Terrain Flythrough.

3. Why a Local, Standalone Tool

DepthWizard is built to run entirely on local compute rather than as a hosted inference service. This was a scoping decision, not a limitation discovered later: GPU inference at any public scale has a real, ongoing cost that this project has no budget for, and the intended user — a scientist or geo-planner inspecting a specific site — is well served by a tool they run themselves. A browser-based viewer (rather than a native desktop application) was kept for the visualization layer specifically because WebGL requires no installation step beyond the local backend already being up.

4. Local REST API Contract (FastAPI)

The backend serves inference results locally over localhost:8000 via three fixed endpoints:

POST /upload • Multipart form (file)
Returns: { "image_id": "uuid", "input_type": "georeferenced" | "non_georeferenced", "metadata": {...} }
POST /process/{image_id}?with_uncertainty=true • Single blocking call
Returns: { "heightmap_png_b64": "...", "confidence_png_b64": "...", "texture_png_b64": "...", "height_min": 0.12, "height_max": 24.87 }
GET /result/{image_id} • Retrieve packaged result or processing status.
